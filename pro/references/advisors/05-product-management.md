# Product management

## When this module loads

- "What should I build next?"
- "Here's my roadmap"
- "Users are asking for X, should I build it?"
- "How do I decide what to cut?"
- Phases 04, 06, 09, 10

## The lens

There are two ways to run a product and only one of them compounds. A build
queue takes requests in and ships them out, and its output is features. A
discovery loop takes a question in and ships an answer out, and its output is
knowledge about what to build. Founders with a queue feel productive and move
sideways.

A roadmap item that cannot name the outcome it changes is a wish. The test is
blunt: what number moves if this ships, and what would you expect to see
within two weeks? An item that fails that test is not necessarily wrong, but it
is uncosted, and it will crowd out something that was testable.

The second question is durability. Anything valuable attracts copying, so the
useful features are the ones that get harder to copy over time, or that improve
as more people use them. A feature that is merely nice is a feature a
competitor ships next month.

For a solo founder the practical form of all this is ruthless scope. The core
loop — the single path that delivers the value — ships. Everything else gets
written down and deferred explicitly, so it is remembered rather than
smuggled in.

## Questions to ask, in order

1. What is the one path through the product that delivers the value?
2. What outcome does the next thing on your list actually change?
3. What number would you expect to move, and by when?
4. How did you decide this was next — a request, a hunch, or a result?
5. Which of the last three things you shipped changed a number?
6. Is this hard to copy, and does it get better as more people use it?
7. What are you deliberately not building, and have you written it down?
8. What would you cut if you had to ship a week from today?

## Red flags in the answer

- "A user asked for it." — One request is not a signal. Ask how many, and what
  they did before asking.
- "It's on the roadmap." — Describes the queue, not the reason.
- "It'll improve engagement." — Which number, from what to what?
- "We need it for parity with competitors." — Parity is a reason to copy, not
  a reason to win.
- "Everything on this list is critical." — Nothing is prioritised.
- "We'll see what happens after we ship." — No expected result means no way to
  learn from the outcome.
- A roadmap with no item that could fail.

## The evidence this module accepts

Scored against `references/evidence-rubric.md`. This module is trying to reach
**score 2** on demand for a feature and **score 3** on whether shipping it
changed anything.

- **Score 3:** a number that moved after a change shipped, measured against an
  expectation written down beforehand.
- **Score 2:** several users independently described the same gap in terms of
  what they currently do instead.
- **Score 1:** a competitor has it.
- **Score 0:** a feature request with no account of the behaviour behind it,
  and any claim that something will improve engagement.

A roadmap item with no expected outcome is marked `UNVERIFIED` and ranked
below any item that has one.

## Output

`references/artifacts/experiment-card.md` — the next build decision written as
a test with an expected result, so shipping it produces knowledge rather than
only features.
